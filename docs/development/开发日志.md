# 开发日志

本日志记录已实际完成的工作、用户真机反馈和据此作出的调整。日期按 Asia/Taipei 记录；阶段报告保留当时的验收边界，后续结论以本日志和「当前进度」为准。

## 2026-11-11 至 2026-11-12：本地账本首版（M0–M5）

完成 Kotlin／Jetpack Compose 原生界面、SQLite 持久化、收入／支出／转账、账目编辑删除、日期与备注、月预算、分类统计及本地模式。金额使用整数分，转账不重复计入收入或支出。

实现通知解析、待确认队列、确认／忽略及本地提醒。候选不会自动入账；当时只验证了合成通知和模拟器流程，没有证明真实支付覆盖。首版源码与交付文档已进入 master，详情见 [M5 交付核验](reports/M5_交付核验.md)。

## 2026-11-12：真实付款通知前提不成立

用户真机测试发现，支付宝、微信在线付款没有系统通知。通知服务只能处理实际出现的通知，修改解析规则或提高后台存活率不能补足缺失的输入。通知渠道因此降为补充，不再作为自动记账主线。

用户常用淘宝、京东、小红书、抖音，以及微信、支付宝自身付款。后续方案必须考虑购物 App 内完成付款、跳转钱包、返回订单页等不同路径，不能把单一支付 App 的结果推定为所有购物场景可用。

## 2026-11-12：页面读取验证（M6）

先实现独立体验包和可手动启动的五分钟无障碍验证：仅尝试读取六个目标 App 的可见页面，在本机内存中保留有限状态词与金额候选，不保存原始页面，不写入待确认队列或账本。设置页区分系统授权、服务连接和采样状态。

加入敏感页面跳过、金额误判、目标来源限制、会话超时、停止／清除和旧结果回写保护的 9 项测试。M6 最终 19 项 JVM 测试与构建通过；模拟输入成功没有被当作真实支付兼容性证据。

随后用户真机反馈读取不顺利、基本读不到。暂停推进无障碍自动读取，保留历史实验入口和记录，默认不采集。该结论没有被扩写为逐个 App、逐个版本都已完成测试。详情见 [M6 页面读取验证](reports/M6_页面读取验证.md)。

## 2026-11-12：桌面主动记账（M7）

用户认可快捷手动记账，明确选择在桌面放一张卡片，点击即可「记一笔」。本轮只实现桌面卡片，截图识别、常用模板和账单导入仍是后续备选。

采用原生 AppWidgetProvider 和 RemoteViews，约 2×1 的暖白卡片，不增加组件库、不定时查询账本。通过显式、不可变 PendingIntent 打开记账表单；提供应用内请求添加与桌面手动添加入口。卡片不要求通知、无障碍或悬浮窗权限，也不展示账目或余额。

针对实际入口补齐冷／热启动、账户异步加载和失败重试、重复点击保留草稿、新建表单重建恢复。验证中修复了两个入口问题：窗口未就绪时过早请求焦点导致冷启动金额框不稳定；把启动动作的已处理标记保存在旧页面 Bundle 中会妨碍新一轮进程恢复。最终改为等待窗口焦点与一帧布局，并用 ViewModel 在配置重建期间保留一次性导航状态。

UI 自动化首先遇到旧 Espresso 3.5.1 的 InputManager 反射与 API 37 不兼容，更新测试依赖至 Espresso 3.7.0／AndroidX JUnit 1.3.0。同时调整 ActivityScenario 场景，使热启动时 Intent 身份变化与测试生命周期观察不冲突，没有删除或跳过失败场景来冒充通过。

最终完整构建通过；19 项 JVM 测试、12 项 Android 17／API 37 模拟器仪器测试全部通过，Lint 为 0 错误、18 警告、4 提示。仪器测试包括 7 项数据库、1 项上下文和 4 项卡片／表单 UI 检查。

在真实模拟器桌面确认添加卡片，结束后台进程后点击，验证金额聚焦、输入 12.50、收起键盘、保存以及首页显示正确。随后只删除验收记录，恢复空测试账本。反复覆盖安装和仪器测试使旧卡片 PendingIntent 失效的现象单独记录；最终流程使用重新添加的卡片验证。保留了真实桌面、输入页与保存后首页截图。

验证仅操作本任务创建的独立模拟器，没有操作用户真机或原账本；验证结束后停止该实例。华为 Mate 70／HarmonyOS 4.3 或更早版本桌面仍需用户确认。详情与安装包哈希见 [M7 桌面记账卡片](reports/M7_桌面记账卡片.md)。

## 2026-11-13：移除无障碍实验（M8）

用户因无障碍授权操作繁琐、读取准确度不足，要求直接移除该部分。删除服务注册、页面读取与会话管理、设置入口、专属资源、9 项专属解析测试和独立 Probe 构建。保留本地账本、桌面快捷记账、草稿恢复和作为补充的通知渠道，数据库结构不变。

先增加安装包能力和设置入口两项 Android 检查，在修改前实际执行，均因旧服务和入口存在而失败。随后移除实现并执行构建、单元测试、Lint 和模拟器回归，结果见 [M8 无障碍移除](reports/M8_无障碍移除.md)。M6／M7 文档保留原始阶段事实并标明历史状态，不再引导开启无障碍或构建旧验证包。

## 2026-11-13：整行消费统计卡片（M9）

根据用户手机桌面截图，保留一行高度，将默认宽度从两列改为四列并支持横向伸展。去掉被截断的应用名，显示今日消费、本月消费和记一笔。两项合计只统计本地正式支出，不计收入、转账或待确认候选；失败显示破折号，避免误显示为零。

将数据库读取放在后台串行执行，写账成功或回到应用后更新；存在卡片时用非唤醒午夜更新及系统周期更新处理日期变化。开机、升级、时间或时区改变后重算，不引入无障碍、联网、常驻服务或精确闹钟授权。旧卡片可能需用户在桌面手动拉宽或重新添加。测试与实际验证边界见 [M9 整行统计卡片](reports/M9_整行统计卡片.md)。

## 2026-11-13：多标签分类与消费平台（M10）

用户确认分类像微信好友标签一样支持多选，原账户改为“消费平台”并保留现金和银行卡。已实现三个常用快捷标签、选择面板搜索和新建、已选标签移除、取消不提交，以及手动记账与通知候选确认共用交互。标签统计允许重叠，总收支、预算和桌面消费不重复累计。

数据库新增有序标签关联，兼容旧分类、原账户 ID、金额、日期、备注和预算；补充微信、支付宝、淘宝、京东平台。验证与安装包以 [M10 报告](reports/M10_多标签与消费平台.md) 为准。

## 2026-11-13：单排标签与三个初始分类（M11）

用户反馈已选与常用分两排重复展示，并确认移除已选计数，选中仅通过底色和小勾表示。改为外部单排，“更多标签”底部面板选择非常用项后排到最左侧，最近选择优先；常用顺延，可见数量取决于屏幕宽度，超出横滑。

用户进一步要求初始标签仅餐饮、交通、购物，其他由用户增加。常用改为可手动固定、排序和独立保存，数据库升级至 v3，保留旧账标签和自建标签，仅清理无账目引用的旧内置预设。验证、安装包校验与限制见 [M11 报告](reports/M11_单排标签与精简预设.md)。

## 2026-11-13：两种桌面尺寸（M12）

用户要求可选 2×1／4×1，小卡片左侧日消费、月消费两行，右侧只保留加号。新增独立小卡片，保留原宽卡片组件与布局，设置页分别提供添加入口。两者共享统计、记账跳转与刷新，仅存在小卡片时也能更新。

实际桌面添加时发现最小宽度导致三格，已调小后确认系统显示 2×1 和 4×1，实际高度一致；模拟消费保存与删除后两种统计同步更新。构建、测试、验收过程及安装包见 [M12 报告](reports/M12_双尺寸桌面卡片.md)。
