# 日常账本：开发计划 v1

日期：2026-11-11。视觉基准：`design/v1/`，名称暂用「日常账本」。

## 本轮交付

一个使用真实本地持久化的原生 Android App，包含记账、账目维护、月收支统计、预算与支付通知待确认流程。界面遵循用户已确认的简洁灰阶风格。

真实手机号／微信认证、云同步、无障碍识别与商业上架分别列为后续依赖，不以占位数据或假成功冒充接入完成。

## 协作方式

| 角色 | 模型与方式 | 责任 |
| --- | --- | --- |
| 计划与验收 | 当前主协调者 | 冻结需求、接收阶段结果、检查实现与证据、汇总 |
| 安卓开发 | `gpt-6-luna`，`max`，一个 worker 子代理 | 顺序实施 M0–M4；阶段报告；修复验收问题 |

用户已明确选择这一模型组合。采用一个开发代理贯穿业务和 UI，避免多人同时改动构建与入口文件。协调者不并行修改代理负责的生产代码。

## M0：构建基线

1. 记录现有代码与构建配置，先运行基线任务。
2. 验证 JDK、Android SDK、Gradle 与本地依赖；保留已有版本，针对真实问题做最小修复。
3. 检查已连接设备／已配置模拟器；没有设备就如实记录，不能把 HTML 渲染当作原生验证。
4. 建立清晰的 `data`、`domain`、`ui`、`notifications` 目录，不引入不必要的多模块、服务端或复杂依赖注入框架。

交付：`reports/M0_构建基线.md`，可复现命令与结果。

## M1：本地账本

数据模型建议：账户、分类、账目、月预算、待确认消费。账目至少包括 ID、类型、金额分、分类、账户、发生时间、备注；转账必须关联来源和目标账户。

实现要求：

- 金额使用 `Long` 整数分；输入最多两位小数，校验空值、零、负数、超限及非法输入，格式化不损失精度。
- 支出、收入、转账分别建模。转账以事务更新双方账户，不计入收支总额。
- 账目可新增、编辑、删除；删除有明确确认，操作后首页、账户与统计同步。
- 账目按实际发生时间倒序分组；月切换、跨年和月底边界使用明确时区处理。
- 收支汇总来自数据库；预算可设置、修改，超支时如实显示。没有预算时展示设置入口。
- 首次启动为空；示例数据若需要，仅存在显式的调试模式，不能混进真实账本。
- 使用本地数据库与仓储接口。优先评估 Room 的兼容性；如引入编译插件代价过高，可采用原生 SQLiteOpenHelper，但必须使用参数绑定、事务与版本化迁移，不得改成一次性覆盖文件。
- 数据库和真实财务数据不写日志，不默认放入不受控系统备份；设置变更持久化，禁止无提示清库。

交付：业务与持久化实现，金额／统计／转账／变更后的重算测试，数据库持久化验证。

## M2：原生界面

1. 首页：月支出、收入、结余、预算、待确认入口、按日分组账目；增加真实空状态。
2. 记一笔：金额键盘、分类、备注、账户和日期选择、保存；复用为编辑与通知补全界面。
3. 统计：支出／收入切换、每日趋势、分类占比，支持月份切换；图表数据与列表汇总一致。
4. 账户入口：本地模式可直接使用；展示手机号和微信入口，但未配置时清楚说明，不发送虚假验证码或伪造登录态。
5. 设置：预算、通知识别开关与授权状态、锁屏金额隐私；尽量沿用既有视觉组件，不扩大导航层级。

约束：原生 Compose，保持灰阶，关闭会改变整体色彩的动态取色。使用 sp 和系统字体缩放，处理状态栏与手势区，主要点击目标至少 48dp；无需一比一复制原型中的小字号。不能用 WebView 包装 HTML 代替原生实现。

交付：可运行原生页面及关键 UI 流程验证；有设备时提供截图与原稿对照。

## M3：支付通知辅助记账

### 授权和输入范围

- 用户先了解用途，再手动开启通知使用权；Android 13+ 单独申请本 App 发送通知的权限。
- 初期识别微信和支付宝的可读系统通知；购物 App 作为按样本增补的适配项，不能宣称已全面覆盖淘宝／京东。
- 明确区分权限被拒绝、没有通知、内容被隐藏、识别不确定和服务正常；不能显示虚假的「全部支付已监控」。
- 只处理明确允许的来源包名。不要请求短信读取、联系人、位置、无障碍或悬浮窗权限。

### 识别和确认

- 通知适配与纯文本解析分离；用脱敏或合成样本测试成功、失败、营销、退款、转账、多个金额、隐私隐藏等场景。
- 只提取可信的消费候选。金额或交易类型有歧义时不得猜测直接入账；可要求用户补全或跳过。
- 同一系统通知的重复推送与更新采用稳定来源键去重；一笔候选多次确认只能形成一条正式账目。
- 不得仅凭相同金额和时间邻近合并跨 App 消费，避免吞掉连续两笔同价交易。缺乏可靠交易标识时交给用户确认可能重复。
- 待确认、确认、忽略具有明确状态。只有确认后进入正式账本；修改使用预填记账页；忽略不影响统计。
- 使用本地系统通知提示，不从后台强行打开完整页面。通知操作使用明确、不可变 PendingIntent，并验证候选 ID 与当前状态。
- 默认锁屏不展示敏感金额；涉及查看或修改详情遵守设备解锁流程。系统通知皮肤由设备决定，不承诺与稿件像素一致。
- 权限撤销与服务重连要能恢复；过滤自身通知，避免循环。未经明确需要，不保留完整原始通知文本。

交付：通知监听、解析、候选队列、确认流程及幂等测试；模拟输入和真实支付实测结果分别标注。

## M4：集成验收

必须记录实际执行的命令与结果，包含：

- Debug APK 构建、针对性单元测试、Android Lint。
- 业务测试先 RED 后 GREEN；覆盖金额精度、聚合、转账、持久化、通知重复与重复确认等风险。测试覆盖率按实际工具报告，不虚报；领域和解析逻辑以不低于 80% 为目标。
- 数据保存后重启仍存在；编辑和删除后汇总一致；收入、支出、转账不会混算。
- 360dp 与常规手机宽度的界面可用；系统字体放大后关键内容可访问。
- 无设备时不得把仪器测试记为通过，列出用户可照做的真机验收步骤。
- 产出安装包路径、功能清单、已知限制与测试报告。

2. 审查待提交文件，排除本地账本、local.properties、密钥、凭据、构建缓存、临时执行日志与本地远程历史备份。

5. 将最终成果提交并推送至master；确认master为默认分支。
6. 对用户明确要求移除的其他远程分支，先本地备份、再删除。没有其他分支时记录实际空集，不伪称执行了删除。

最终交付先完成代码与设备验收，再上传经审查的源码快照；不提前推送未完成代码。

## 交付节奏

开发代理完成每个里程碑时向协调者报告，并写入 `reports/`。可独立继续的本地步骤不等待重复批准；遇到账号、设备、付费或外部发布依赖时记录依赖，继续不受影响的工作。出现构建失败先定位真实原因，不连续重试相同失败命令，不削弱测试冒充通过。
