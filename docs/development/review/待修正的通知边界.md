# 通知边界审查与修正记录

协调者基于M1代码发现的问题与后续修正记录。以下问题描述指最初实现；当前状态单独列出，不能将历史问题误读为已经验证的当前行为。

## 金额必须完整匹配

初始`NotificationParser.explicitAmounts`可能把`支付成功 ¥28.001`截取成`28.00`后传给金额校验，使原本超过两位小数的文本被误认为有效支出。类似地，数值后面的不合法字符或不规范分隔不能通过局部匹配变成另一个金额。

修正要求：在解析候选之前确认完整数值边界。为 `¥28.001`、`28.001元`、合法 `¥28.00`、合法分组金额、 malformed分组等加针对性测试；超精度应转待核对或跳过，不得悄悄截断。

当前状态：已修正并经历实际RED→GREEN。额外覆盖`28..50元`、`1e3元`、`-28元`，避免从畸形token中截取局部金额。相关批次10项JVM测试通过。

## 通知槽位标识不等于永久交易标识

初始`NotificationIdentity.idFor(packageName, notificationKey)`仅按包名与系统key生成持久ID。AOSP的StatusBarNotification key由用户、包名、id、tag、uid及部分分组字段组成，不含发布时间；同一App可用同一id/tag发下一笔通知。

来源：[AOSP StatusBarNotification.java](https://android.googlesource.com/platform/frameworks/base/+/main/core/java/android/service/notification/StatusBarNotification.java)。

风险：第一笔候选确认／忽略后，后续复用同一通知槽位的新消费可能被当作已经处理而永远跳过。

修正要求：区分同一通知生命周期内的更新与复用槽位的新事件。明确重连／移除／重发的语义，不仅依赖永久 key；不得以相同金额加邻近时间作为唯一交易去重条件。

最少验收：

- 同一事件重复回调和更新只产生一个候选。
- 同一系统 key 在前事件移除后再用于新支付，能够产生新候选，且不受前一候选已确认状态影响。
- 两笔同价支付不会被无依据合并。
- 服务重连和已处理候选不会引发重复入账。

当前实现：采用包名、key与`notification.when`的哈希；没有有效when时回退postTime。相同事件时间的重放复用候选，同key不同事件时间分开。服务重连重新读取活跃通知；已处理候选不会恢复为待确认，正式确认仍受SQLite事务及唯一约束保护。

限制：第三方改变when、复用when或缺少可靠交易标识时，仍可能出现重复候选或漏识别；这不是交易流水接口，不能承诺完美交易去重。所有候选必须人工核对后确认。最新事件ID和完整通知链路仍待M4最终测试。

## 现有测试的证据边界

Android14模拟器已实际运行6项SQLite仪器用例，验证持久化、转账、候选更新与最多一次确认，另外1项应用上下文用例通过。最新通知生命周期及提醒流程的最终结果以M4报告为准。微信／支付宝真实支付未实测，不能把合成样本测试描述成平台覆盖证明。
